# ADR-002: Use a QualitySignal Model for Standardized Evidence

## Status

Accepted

## Context

The SDET Reliability Framework collects evidence from multiple sources.

Evidence may come from:

- API health checks
- Playwright tests
- Python tests
- Prometheus metrics
- Synthetic canaries
- Security workflow validation
- Performance trend checks
- Release-readiness scripts

Without a common model, each source would produce different output formats and the release assessment logic would become harder to maintain.

The framework needs a consistent way to describe quality evidence regardless of where that evidence originated.

## Decision

Use a standardized `QualitySignal` model to represent quality and reliability evidence.

Each evidence provider should return a signal that can be evaluated by the release assessment layer.

A signal may represent health, failure, performance, observability, risk, or readiness information.

## Alternatives Considered

### Use raw test output only

The framework could rely only on raw Pytest or Playwright output.

This was rejected because raw test output is useful for debugging, but not ideal for release decision support.

### Create separate assessment logic for each tool

Each evidence source could have its own custom assessment logic.

This was rejected because it would create duplicated logic and make the release engine harder to extend.

### Use only pass/fail status

The framework could reduce all evidence to pass or fail.

This was rejected because reliability decisions often require more context than simple pass/fail results.

## Consequences

### Positive Consequences

- Evidence from different tools can be evaluated consistently
- Release assessment logic becomes easier to extend
- The framework can support new evidence providers over time
- Quality signals can represent health, risk, degradation, and readiness
- The design supports evidence-driven release decisions

### Tradeoffs

- Evidence providers must map their results into the common model
- The signal model must remain simple enough to avoid overengineering
- Additional documentation is needed so future contributors understand the pattern

## Outcome

The `QualitySignal` model supports the framework’s central idea: quality decisions should be based on standardized evidence.

This allows the project to move beyond isolated test execution and toward structured release-readiness assessment.
